# LoRA Fine-tuning: optimized ViT deployment

End-to-end image classification pipeline on EuroSAT (10 land-use classes) with a Vision Transformer:
LoRA fine-tuning, INT8 quantization, a FastAPI inference service, Docker, and CI with GitHub Actions.

## Pipeline

| Step | Command | Output |
|---|---|---|
| Fine-tune ViT with LoRA, keep the best epoch | `py train.py` | `checkpoints/best_lora_weights.pt` |
| Evaluate the best adapter on the test split | `py evaluate.py` | loss / accuracy / macro-F1 |
| Merge LoRA into the base weights and quantize to INT8 | `py quantize.py` | `artifacts/model_int8.pt`, `artifacts/model_meta.json`, size/accuracy report |
| Serve | `py -m uvicorn app.main:app --port 8000` | API on http://localhost:8000 |

Settings live in `configs/config.yaml` (CPU-friendly subset). `configs/config.kaggle.yaml` is the
full-dataset GPU run: `py train.py --config configs/config.kaggle.yaml`.

- **LoRA** (`vit_lora/lora.py`): rank-32 adapters on the query/value projections of the last three
  transformer blocks. Only the adapters and the classifier head train (~0.35% of the parameters).
- **Quantization** (`vit_lora/quantization.py`): the adapters are merged into the base weights, then
  every `nn.Linear` is dynamically quantized to int8, which cuts the model to roughly a quarter of its size.

## API

| Endpoint | Description |
|---|---|
| `GET /health` | Liveness check |
| `GET /labels` | The classes the model predicts |
| `POST /predict?top_k=3` | Multipart image upload, returns a `request_id`, the label, confidence and top-k classes |
| `POST /feedback` | `{"request_id": ..., "label": ...}`: the true label for an earlier prediction |
| `GET /monitoring/drift` | Data and prediction drift of the latest window vs the training reference |
| `GET /monitoring/performance` | Live accuracy / macro-F1 / per-class recall from the labelled predictions |
| `GET /metrics` | Everything above as Prometheus metrics, plus HTTP and resource metrics |

```bash
curl -X POST http://localhost:8000/predict -F "file=@image.jpg"
```

Interactive docs are at http://localhost:8000/docs.

## Docker

```bash
docker build -t vit-lora-api .
docker run -p 8000:8000 -v "$(pwd)/artifacts:/app/artifacts" -v vit-monitoring:/app/monitoring_data vit-lora-api
```

The image holds only the inference code and its dependencies. The quantized model produced by
`quantize.py` is mounted at run time, so model binaries stay out of git and out of the image.

## Observability

The service monitors itself at three levels, all exported at `/metrics` and scraped by Prometheus.

| Level | What is watched | How |
|---|---|---|
| **Data drift** | Brightness, contrast, R/G/B means, saturation and sharpness of each input image | Compared with the training split over the last `DRIFT_WINDOW` (200) predictions: PSI per feature (drift at PSI >= 0.25) plus a KS test for evidence |
| **Prediction drift** | Predicted-class mix and top-1 confidence | PSI against the model's outputs on the validation split; needs no labels |
| **Model performance** | Accuracy, macro-F1, per-class recall | Joins predictions with labels sent to `/feedback`, over the last `PERFORMANCE_WINDOW` (200) labelled predictions, against the validation baseline |
| **Service** | Request rate, status codes, latency, model forward-pass time | FastAPI middleware + histograms |
| **Infrastructure** | Host CPU / memory / disk / network, per-container CPU and memory, API process RSS / CPU / threads | node-exporter, cAdvisor, and a psutil collector inside the API |

Every prediction and every label is logged to SQLite (`$MONITOR_DIR/predictions.db`) with the model's
content hash, so drift and accuracy survive restarts and can be traced back to a model version.

```bash
py build_reference.py                    # once per model: artifacts/reference_profile.json
docker compose up -d --build             # API :8000, Prometheus :9090, Grafana :3000
py simulate_traffic.py --phases clean:250 dark:300 --label-rate 0.5
```

- Grafana: dashboard **ViT-LoRA AI observability** (admin / admin, or anonymous read-only). It has
  sections for service health, model outputs, data drift, performance and infrastructure.
  It is generated by `observability/grafana/make_dashboard.py`.
- Prometheus alerts (`observability/prometheus/alerts.yml`): `InputDataDrift`, `FeatureDrift`,
  `PredictionDrift`, `ConfidenceDrift`, `ModelAccuracyDegraded`, `HighLowConfidenceRate`,
  `ModelAPIDown`, `HighErrorRate`, `HighPredictLatency`, `HostHighCPU`, `HostHighMemory`,
  `HostDiskAlmostFull`, `APIMemoryHigh`.
- `simulate_traffic.py` replays held-out test images (optionally corrupted: `dark`, `bright`, `haze`,
  `noise`, `blur`, `grayscale`) and sends the true label back for `--label-rate` of them.

Result of the command above on the INT8 model, in the Docker stack:

| Phase | Accuracy on labelled requests | Drift status | PSI brightness / blue mean | Confidence PSI | Mean confidence |
|---|---|---|---|---|---|
| clean (250 requests) | 0.974 | ok, no feature drifted | 0.11 / 0.04 | low | 0.977 |
| dark (300 requests) | 0.838 | drift on 6 of 7 features (all but saturation) | 5.25 / 7.70 | 0.75 | 0.885 |

Validation baseline: accuracy 0.947, mean confidence 0.945. Darkening the images leaves the
predicted-class mix almost unchanged (PSI 0.03), so here prediction drift alone would have missed
it. Input-feature drift and the confidence shift show the problem before any labels arrive.

## Tests

```bash
py -m pip install -r requirements-dev.txt
py -m pytest tests -v
```

The tests use a tiny randomly-initialised ViT, so they need no dataset, download or GPU.

## Branches and CI

- `main`: stable, deployable code.
- `develop`: integration branch; work is merged into `main` from here.

`.github/workflows/ci.yml`:

| Job | Runs on | What it does |
|---|---|---|
| `test` | push to `main` or `develop`, PR into `main` | installs dependencies, runs pytest |
| `build` | same, after `test` passes | builds the Docker image and checks the app imports inside it |
| `deploy` | push to `main` only, after `build` passes | pushes the image to GitHub Container Registry |
